## 验证记录（2026-10-28）

真机往返，目标 `165-东安实业测试`（192.168.2.165，CentOS 7，宿主 .152），操作前为开机状态：

| 操作 | 耗时 | 结果 |
|---|---|---|
| 优雅关机 | 93.4s / 94.6s（两次） | `poweredOff`，Tools 变 `guestToolsNotRunning` |
| 开机 | 2s / 3s | `poweredOn`，Tools 随后回到 `guestToolsRunning` |
| 优雅重启 | 105.4s | 全程 `poweredOn`，Tools 掉线后重新回到 `guestToolsRunning` |

负路径（都不改变虚拟机状态）：

| 场景 | 结果 |
|---|---|
| 对已开机机器点开机 | `state`：这台虚拟机已经是开机状态 |
| 对已关机机器点关机 | `state`：这台虚拟机没有在运行，不需要关机 |
| 对 Tools 未运行的机器点关机（220-Windows跳板机-勿动） | `tools`：客户机 VMware Tools 没在运行，无法优雅关机，只能用强制断电 |
| 未知 host_id | HTTP 404 |
| 未知 action | HTTP 400 |

## 实现取舍

- 操作是"提交任务 + 轮询"，不是长连接：`POST /api/vms/power` 立刻返回 `task_id`，
  后台线程跑 `ShutdownGuest/RebootGuest/PowerOnVM_Task`，页面每 1.5 秒查一次
  `GET /api/tasks/<id>`。关机/重启本来就要一两分钟，同步等待会把 HTTP 连接挂死。
- **不能靠 `runtime.bootTime` 判断"重启完成"**：它是客户机时钟推算出来的，实测同一台
  机器没重启也能从 11:40:47 跳到 11:42:48。改成看 Tools 是否"掉线后又回来"——优雅重启
  全程 `poweredOn`，电源状态根本不翻。
- 属性一律用 `PropertyCollector` 重新取，不直接读 managed object 上的属性（那是旧快照）。
- 成功后只把这一行的会变字段（电源/Tools/IP/开机时间）就地更新，顺手重算该主机的
  "N 开机"数字，不重新采集三台主机。
