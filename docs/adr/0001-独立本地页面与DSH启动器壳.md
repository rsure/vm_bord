# 用独立本地页面 + DSH 启动器壳，而不是把看板做成 DSH 内嵌面板

DSH Desktop 的客户端插件跑在宿主 SPA 里，官方规范明确禁止用 iframe 嵌入 Host 托管的 HTML（`practices.md:33`：iframe 文档拿不到宿主的主题变量、深浅色切换和 `ctx.locale`）。同时第三方插件的客户端必须预先构建成单文件、`pnpm pack` 后安装，且每次改代码都要**手动完整重启 Desktop** 才生效。看板这类界面一开始必然反复调整，做成插件面板的迭代成本极高。

因此主体是一个独立的本地 Python 服务 + 静态页面（浏览器访问 `127.0.0.1`），DSH 侧只做一个极简启动器面板：探测服务健康、拉起进程、打开浏览器。用户原始需求里的"跟 harness 一起启动"落地为"在 harness 里一键拉起"。

## Considered Options

- **DSH 客户端插件面板**（`sidebar.panellist` + `main` slot）：入口最原生，但禁 iframe、CSS 直接注入 document 无隔离、要求 React 单文件产物、每次改动要重启 Desktop，且官方没有最小可用示例（现存样板都是混淆产物，只能摸着写）。
- **Desktop 工作台**（`ctx.desktopWorkbenches.register()`）：定位最贴"整页业务面板"，有 295 行开发规范，但开发链路同样受限，还要接入工作台市场的身份体系。

## Consequences

- "同一个页面既能当插件、又能单独启动"在 DSH 里无法实现 —— 客户端 bundle 必须经 `window.__ModuleLoader__.load()` 挂进宿主，`apps/web` 不是独立应用。实际形态是"独立页面 + 一个只会开浏览器的壳"。
- 启动器插件改一次要重启一次 Desktop，所以它的功能边界必须一次定死：只管拉起、停止、打开浏览器，不往里加看板功能。
- 好处是看板迭代完全不受 DSH 约束，改完刷新浏览器即可。
